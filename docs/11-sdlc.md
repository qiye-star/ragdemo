# 11 · SDLC：开发生命周期、工作流分解与并行计划

本文档回答三个问题：**怎么开发**（生命周期与流程规范）、**分哪几步**（工作流分解与依赖）、
**哪些能并行**（并行分析与人力约束）。

与 [10-roadmap.md](10-roadmap.md) 的分工：

| | `10-roadmap.md` | 本文档 |
|---|---|---|
| 回答 | **交付什么**：P0–P6 各阶段的产出与**阶段级**验收 | **怎么交付**：流程规范、工作流分解、依赖与并行、**工作流级**出口条件 |
| 粒度 | 阶段（2–5 周） | 工作流（3–10 天） |
| 谁看 | 所有人，尤其是判断「这个阶段能不能收」 | 排期、分工、执行时看 |

**阶段验收以 `10-roadmap.md` 为准**，本文档不重复阶段级指标，只补细到工作流的出口条件。
两者冲突时以 `10-roadmap.md` 为准并提 PR 修正本文档。

## 2. 生命周期模型

### 2.1 双层节奏

**外层：阶段门禁（Phase Gate）**——P0–P6，每阶段有一组不可妥协的量化验收
（[10-roadmap.md](10-roadmap.md)）。**上一阶段未通过验收不进入下一阶段**，
唯一例外见 §5.3 的并行豁免。

**内层：周迭代**——阶段内以 1 周为一个迭代。每周一排期、周五演示与回顾。
一个迭代交付 1–3 个工作流任务，每个任务都是可独立测试的交付物。

选双层而非纯敏捷，是因为本项目有**不可回退的正确性约束**：时点一致性、溯源、合规。
这些东西「先上线再迭代」的代价是把错误数据写进历史库，而历史库按设计是不可删的
（[03-point-in-time.md](03-point-in-time.md) §3.2）。阶段门禁就是为它们准备的。

### 2.2 五个环节的准入准出

| 环节 | 准入（DoR） | 产物 | 准出（DoD） |
|---|---|---|---|
| 需求 | 需求落在 `00-overview.md` §5 的范围内，或已明确决定调整边界 | 一句话目标 + 验收标准 | 验收标准可量化或可执行验证 |
| 设计 | 需求已确定 | 对应专题文档的修改 PR；涉及不可逆决策则加一篇 ADR | 文档合并，接口签名与 DDL 确定 |
| 实现 | 设计文档已合并；依赖的上游工作流已交付 | 代码 + 测试 | §2.4 的 DoD 全部满足 |
| 验证 | 实现已合并到主干 | 评测报告 | CI 门禁全绿；阶段验收项达标 |
| 发布 | 阶段验收通过 | 打 tag，更新 runbook | 回滚演练过一次 |

### 2.3 Definition of Ready（任务可以开工的条件）

- [ ] 任务在某个工作流（§3）下，有编号
- [ ] 它依赖的上游工作流已交付，或上游已提供 Mock 与契约测试
- [ ] 验收条件写成了可执行的命令或可查的数字
- [ ] 涉及的接口签名已在对应专题文档中定稿
- [ ] 若改动数据库，迁移脚本的方向已确定（只加不改，见 §4.2）

### 2.4 Definition of Done（任务可以合并的条件）

- [ ] **先有失败的测试，再有实现**（`CLAUDE.md` §3）
- [ ] 数值计算与时点逻辑有单测，没有例外
- [ ] `ruff` + `mypy` 通过，类型注解完整
- [ ] 外部适配器有 Mock 与契约测试
- [ ] CI 三套评测全绿，数字贴进 PR 描述
- [ ] 日志结构化且含 `run_id` / `as_of` / `entity_id`
- [ ] 代码与日志中无密钥
- [ ] 对应专题文档已同步（文档是契约，代码改了文档没改 = 未完成）

最后一条容易被跳过。**文档与代码不一致时以文档为准**（`docs/README.md` 开头），
所以实现偏离文档必须回头改文档，否则下一个人会按文档写出冲突的代码。

拖到工程做完再开始，就等于把它们从「并行」变成「串行」，直接给工期加两周。

### 4.2 数据库迁移的依赖约束

迁移脚本**只加不改**。已上线的迁移不得修改，纠错靠新增一条迁移。
这条约束让「多人并行改 schema」成为可能——每人加自己的迁移，按序号合并即可，
不会出现「两个人改同一个建表语句」的冲突。

破坏性变更（删列、改类型）需要三步走，跨两个发布：
加新列 → 双写并回填 → 下个发布再删旧列。中间任何时刻回滚都不丢数据。

## 5. 并行分析

### 5.1 理论上可并行的组

| 组 | 内容 | 可并行的前提 |
|---|---|---|
| **A** | W1.3 Tushare / W1.4 EDGAR / W1.5 公告 Mock | W1.1 抽象与 W1.2 中间件已定稿 |
| **B** | W3.2 BM25 一路 / W3.3 向量一路 | W3.1 骨架与 `RetrievalRequest` 已定稿 |
| **C** | W4.5 基本面 / W4.6 事件 / W4.8 政策 | W4.1 外壳层与 `Claim` 契约已定稿 |
| **D** | W6.1 评测框架 / W7.4 备份 / W7.6 出网代理 | 只依赖 W0，与主线完全解耦 |
| **E** | W9 全部 | 无代码依赖 |
| **F** | W7.1 模板渲染 / W7.3 CLI | 依赖 W3（取证据）但不依赖 W4（可用假数据） |

**并行的前提全都是「接口先定稿」**。这不是巧合——[adr/0005](adr/0005-announcement-provider-abstraction.md)
的「先定接口、不定供应商」正是同一个手法：先冻结契约，再让实现并行推进。
项目中每一处可并行的地方，都对应一个先行定稿的接口。

### 5.2 实际能并行多少：人力才是瓶颈

团队是 **1 位技术负责人（待招，前期外包过渡）+ 0–1 位数据工程师 + 2–3 位创始人**
（[00-overview.md](00-overview.md) §3）。也就是说工程侧**最多 2 条并行轨**，
常态可能只有 1.5 条。

上面列了 6 个可并行组，但一次只能开 2 个。所以并行分析的实际用途不是「同时开工六摊」，
而是**决定当某条轨被阻塞时，另一条轨该切到哪里**。按这个用途给出推荐编排：

| 阶段 | 轨 1（技术负责人，主线） | 轨 2（数据工程师 / 外包，支线） | 轨 3（创始人，全程） |
|---|---|---|---|
| P0 | W0.1 → W0.2 → W0.3 → W0.4 → W0.5 | W0.6 种子导入工具 | **W9.1 数据录入、W9.2 供应商评估** |
| P1 前段 | W1.1 → W1.2 → W2.1 → W2.4 | W1.3 Tushare → W1.4 EDGAR → W1.6 Dagster | W9.1 收尾 → W9.2 |
| P1 后段 | W3.1 → W3.2/W3.3 → W3.4 → W3.5 → W3.6 | W1.5 公告 Mock → W1.7 实体解析 → W2.2/W2.3/W2.5 | **W9.3 检索评测集 100 条** |
| P1 尾 | W6.1 → W6.2 + CI 集成 | W7.4 备份演练、W7.6 出网代理、W8.1a 内部诊断接口 | W9.3 收尾 |
| P2 | W4.1 → W4.2 → W5.1 → W4.5 | W7.1 模板 → W7.2 推送 → W7.3 CLI | **W9.4 抽取评测集 50 条** |
| P2 尾 | W5.2 合规过滤 → W5.3 哈希链 | W6.3 抽取评测指标 | W9.4 收尾 |
| P3 | W4.3 → W4.6 → W4.7 → W4.9 → W4.10 | W1.8 RSS/政策 → W6.5 价格分 | **W9.5 判断评测集、W9.6 观点确认** |
| P3 尾 | W6.6 论据分 → W6.7 报告分组 | W7.5 监控成本 | W9.6 常态化 |
| P4 | W8.1b → W8.2 | W5.4 RLS → W8.3 上传 → W8.4 导出 | W9.7 合规文案 |
| P5–P6 | W8.5 → W8.6 | 按需 | 持续 |

### 5.3 唯一的跨阶段并行豁免

P1 验收含**双跑一致性测试**，需要间隔一周
（[03-point-in-time.md](03-point-in-time.md) §5.1、[10-roadmap.md](10-roadmap.md) P1）。
这一周**不应该空等**：允许 P2 的 W4.1（工具外壳层）与 W7.1（模板渲染）提前开工，
因为它们不依赖 P1 的验收结论，只依赖 W3 的接口。

**这是唯一的豁免。** 若双跑测试失败，提前开工的这两项要回炉——这个风险是划算的，
因为它们本来就是纯接口层工作，返工面小。其他任何跨阶段提前开工都要走变更审批。

### 5.4 不能并行的三处

写清楚更重要，因为这三处是最容易被排期表误伤的地方：

1. **W1.2 时点写入中间件是全部入库路径的唯一闸门。** 在它定稿前不要并行写任何适配器的
   入库逻辑——那些代码会在中间件定稿后全部返工。适配器只做「拉取 + 归一化」，
   入库交给中间件，这个边界是并行的前提也是它的上限。
2. **W3.1 骨架未定稿前，BM25 与向量两路不能分头做。** 两路的过滤条件、`LIMIT`、
   返回结构必须一致才能融合，先分头做必然对不齐。
3. **W0 内部完全串行。** W0.4 的权限依赖 W0.3 的表，W0.5 的不变量测试依赖 W0.4 的视图。
   想并行 W0 只会制造返工。

## 6. 变更控制

不同类型的改动走不同的流程，这决定了一个 PR 需要几个人看：

| 改动类型 | 流程 | 审核人 |
|---|---|---|
| 实现细节（不改接口） | 普通 PR + CI 门禁 | 1 人 |
| 接口签名 / 数据契约 | 先改专题文档 PR，合并后再改代码 | 1 人 + 受影响工作流的负责人 |
| 数据库 schema | 新增迁移（只加不改），更新 [02](02-data-model.md) 与 `bitemporal_registry` | 1 人 + 跑 Schema 不变量测试 |
| Prompt | 版本化新文件，跑三套评测，数字贴 PR | 1 人 |
| 检索参数（权重 / `k` / `ef_search`） | 跑检索评测对比，写进 `eval_run` | 1 人 |
| 评分阈值（±3% / ±8%） | 改 [08](08-evaluation.md) 并注明生效日期，**不得回溯重算历史分数** | 2 人 |
| **合规词表** | CODEOWNERS 强制 | **2 人** |
| **[adr/](adr/README.md) 中的七项决策** | 新增一篇 ADR，写明推翻条件与迁移路径 | **全体** |
| 范围边界（[00](00-overview.md) §5 非目标） | 先讨论边界，不默默扩张 | **全体** |

## 7. 环境与发布

| 环境 | 用途 | 数据 | 谁能访问 |
|---|---|---|---|
| `local` | 开发 | Mock + 少量真实样本 | 开发者 |
| `ci` | 自动化测试 | 固定夹具，每次重建 | CI |
| `staging` | 阶段验收、评测基线 | 真实数据的子集（20 家实体） | 团队 |
| `prod` | 生产 | 全量 | 团队 + 用户（P4 起） |

**发布流程**：主干打 tag → 在 `staging` 跑全量评测 → 对比基线 → 通过则部署 `prod` →
观察 24 小时 → 更新 runbook。

**回滚**：应用回滚到上一个 tag；**数据库不回滚**——迁移只加不改，旧代码能在新 schema 上运行
（这正是 §4.2 三步走约束的目的）。若某次迁移确实无法向后兼容，它必须拆成三步分两个发布做。

## 8. 每阶段的可执行计划

本文档给的是工作流与编排。**具体到「先写哪个测试、再写哪行代码」的计划，
每个阶段单独一份**，放在 [`superpowers/plans/`](superpowers/plans/)：

| 阶段 | 计划文件 | 任务数 | 状态 |
|---|---|---|---|
| P0 | [2026-09-21-p0-foundation.md](superpowers/plans/2026-09-21-p0-foundation.md) | 14 | 可执行 |
| P1a 数据接入 | [2026-09-21-p1a-ingestion.md](superpowers/plans/2026-09-21-p1a-ingestion.md) | 10 | 可执行（依赖 P0 验收） |
| P1b 文档管线 | [2026-09-21-p1b-document-pipeline.md](superpowers/plans/2026-09-21-p1b-document-pipeline.md) | 9 | 可执行（依赖 P1a） |
| P1c 检索与验收 | [2026-09-21-p1c-retrieval-and-acceptance.md](superpowers/plans/2026-09-21-p1c-retrieval-and-acceptance.md) | 11 | 可执行（依赖 P1b） |
| P2 | 待写 | — | P1 验收通过后编写 |
| P3–P6 | 待写 | — | 依次 |

**P1 为什么拆成三份**：它横跨三个独立子系统，每份都能独立产出可测试的软件
（P1a 交付「数据能按时点正确入库」，P1b 交付「文档切块 + 向量化入库」，
P1c 交付「`RetrievalService` + P1 全部验收指标」）。一份 30 任务的计划既不便于
分轨执行，也不便于中途调整。

**P1a/P1b/P1c 在 P0 执行之前编写**，因此它们对 P0 产出物的接口只是**假设**。
每份计划开头都有一张「对上游的接口假设」表；P0 跑完若有出入，按表回改。

**为什么不一次写完全部阶段**：后续阶段的任务细节取决于前一阶段的实测结论
（`pg_search` 的实际行为、种子数据的实际质量、Mock 与真实数据的差距、
检索召回的真实水平）。现在写 P3 的逐步任务，等做到 P3 时至少一半要重写。
每阶段验收后再写下一份，是为了让计划保持「可直接执行」而不是「看起来很全」。

P1 是例外——它被提前写出来了。代价已经在上面标明：接口假设未经 P0 验证。
P0 验收后应先核对三份计划的假设表，再开始执行 P1a。
