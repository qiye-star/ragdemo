# 10 · 分阶段任务与验收

验收标准全部可量化或可执行验证。**「基本完成」不是验收标准**——
每一条都必须是一条能跑的命令或一个能查的数字。

> **本文档回答「交付什么」。** 怎么交付——开发流程、工作流分解到 3–10 天粒度、
> 依赖图与并行编排、变更控制——见 [11-sdlc.md](11-sdlc.md)。
> 具体到「先写哪个测试、再写哪行代码」，见 [`superpowers/plans/`](superpowers/plans/)
> 下当前阶段的实施计划。
>
> 阶段验收以本文档为准；`11-sdlc.md` 只补细到工作流的出口条件，两者冲突时改后者。

**P1 实跑结果**（`make lint && make typecheck && make test && make accept-p1`）：
三道门全绿，全量 **488 passed / 1 skipped**。但**九项验收里只有四项拿到了真实结论**，
其余五项跑绿不等于通过，逐条如下——把它们无限定地记成「通过」等于给没验过的东西发合格证：

| # | 检查 | 实际状态 |
|---|---|---|
| 1 | Dagster 连续 5 天无人工干预 | ⚠️ 结构性替代：只验了重跑幂等，没有真实的连续 5 天无人值守 |
| 2 | `recall@10 > 0.80` | ⚠️ 跑在夹具语料的 **5 条**自造用例上；`06-retrieval.md` §9.2 要的是 **100 条生产用例** |
| 3 | `recall@50 > 0.92` | ⚠️ 同上 |
| 4 | 索引召回率 ≥ 0.95 | ✅ 真验（对精确扫描逐条比对） |
| 5 | p95 延迟 < 3s | ⚠️ 数字真实，但 6 个块的语料不代表生产规模 |
| 6 | 双跑一致性 | ⏸️ 已写基线快照，**需满 7 天后重跑**才算完成；快照目前落在 gitignored 的 `.superpowers/`，`git clean -fdx` 会把七天计时清零且无提示 |
| 7 | 时点泄漏自检 5 条 | ✅ 真验 |
| 8 | 备份恢复演练 | ⚠️ 只验了脚本不变量，没有驱动真实恢复（真跑会覆盖现有库） |
| 9 | `EXPLAIN` BM25 下推 | ✅ 真验 |
| 附 | PG↔Chroma 偏移收敛到 0 | ✅ 真验（[adr/0009](adr/0009-chroma-as-vector-candidate-generator.md) 后果 2） |

**结论：代码层面 P1 的 11 项做完 9 项，验收层面不能宣布 P1 通过。**
第 2、3 项缺真实评测集（W9 手工工作流），第 1、6、8 项缺真实运行时间与演练窗口。

## 阶段与工作流的对应

每个阶段由哪些工作流构成、哪些能并行、推荐怎么编排三条轨，见
[11-sdlc.md](11-sdlc.md) §3（工作流分解）与 §5（并行分析）。

一条容易被排期表误伤的事实：**创始人的手工工作流 W9（种子数据、供应商评估、
评测集标注、观点确认）在关键路径上，且必须第 1 天启动。** 它零代码依赖，
拖到工程做完再开始就等于把并行变成串行。

## 关键路径与风险

| 风险 | 影响阶段 | 缓解 |
|---|---|---|
| 公告供应商迟迟未定 | P1 | 抽象接口 + Mock 让下游不阻塞（[adr/0005](adr/0005-announcement-provider-abstraction.md)） |
| `pg_search` 版本语法与文档不符 | P0 | P0 就执行一遍全部 DDL，实测为准 |
| 中文分词效果不佳导致召回不足 | P1 | `chinese_lindera` 与 `chinese_compatible` 两套方案在评测集上对比 |
| 嵌入 API 限速拖慢首次入库 | P1 | 批处理 + 缓存 + 断点续传；必要时分批上线实体 |
| 手工关系的乐观偏差掩盖真实能力 | P3/P5 | 报告强制分组（`08-evaluation.md` §3.1） |
| 观点样本量不足以支撑准确率宣称 | P5 | 样本量下限规则（§3.2） |
| 技术负责人未到位 | 全程 | P0–P1 的骨架与规范先行，降低交接成本 |
