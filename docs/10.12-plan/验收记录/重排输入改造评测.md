# 重排输入改造评测（2026-10-13）

## 1. 改了什么

重排模型以前只看到块的裸正文，现在可以选择让它看到和嵌入完全相同的文本：文档标题 + 章节路径 + 描述 + 正文（超长截断规则同嵌入，`embedding_input`）。

- 开关：`RetrievalConfig.rerank_rich_input`，**默认关闭**；评测命令加 `--rerank-rich-input`。
- 没有迁移，没有改 gold 块 id，没有改 prompt 和切块。
- 顺带：`eval run` 现在把逐题排名写进 `eval_run.metrics.per_question`（现有 JSON 列，无迁移）。每题记录 gold 里最靠前者在 BM25、向量、融合、重排、最终输出里的名次（不在候选里记为空）。注意重排名次只记到最终 top-10，超出的显示为空；要看完整重排名次得另行扩大 top_n。
- 提交：`39993ae`。测试先写后实现（3 条新增测试先失败），tests/retrieval 与 tests/evals 共 182 条通过；ruff 与 mypy --strict 对改动的文件通过（仓库里另有一处与本次无关的 `census.py` E501，原来就有）。

## 5. 必须一起看的警告

1. **auto 题有“自己出题自己考”的偏差。** table/auto 题是看着“描述 + 正文”写出来的，新的重排输入里正好有描述；other 题的标题也被带进来。所以 table MRR 从 0.27 涨到 0.69 这种幅度，部分是被测集对这种输入天然友好。分析文档里同样提醒过 table/auto 只能作回归护栏。**在人工标注的表格集到位、并在那份集合上复测之前，不能把这个增益当作真实线上效果。**
2. **延迟明显变差。** p50 从约 1 秒到 6.4 秒，p95 到 13.9 秒。输入变长是原因之一，但只有一次运行，无法排除重排接口当时本身变慢。采纳前要在同一时段各跑一次相同口径的小样本延迟对比；若确认是输入变长造成，可考虑把截断长度缩短（例如 1000 字）或只对表格块使用。这一项不在计划门槛里，但会影响线上体验。
3. 只做了 C2 一次（硬上限两次，实际付费评测只用了 1 次 C2，没有第二次）。`eval_extraction` 和观点评分两套评测与本改动无关（重排输入不影响抽取），本次没有重跑。

## 6. 结论与建议设置

- 按计划门槛：通过，可采纳。
- 默认值：**保持关闭**，由负责人决定是否打开。
- 建议设置：打开 `rerank_rich_input`，同时保持 `rerank_enabled=true`；打开之前先完成上面第 2 条延迟复核，并用人工表格集复测增益。
- 花费：付费评测 1 次 C2（100 题 × （1 次嵌入 + 1 次重排）；R@50 的宽检索不走重排）。无 TextIn、无 LLM 生成调用。

## 延迟复测（2026-10-13，同一时段连续两次付费运行，标签 lat-retest-off / lat-retest---rerank-rich-input）

| 开关 | 综合 R@10 | MRR@10 | p50 | p95 |
|---|---|---|---|---|
| 关（原行为） | 0.7500 | 0.5328 | 1016 ms | 1340 ms |
| 开（丰富输入） | 0.8700 | 0.7708 | 1165 ms | 6259 ms |

结论：中位数只多约 150 ms；上一次的 6.4 秒中位数主要是当时重排接口慢，不是输入变长。p95 仍从 1.3 秒升到 6.3 秒，说明有少数请求（输入较长的表格块）明显更慢，尾部延迟需要关注。召回与 MRR 复现（0.87，MRR 0.7708 对 0.7658，噪声量级）。待办：缩短截断长度或对表格块单独限长后再测 p95；仍需人工表格题验证循环论证问题。开关仍默认关闭。
