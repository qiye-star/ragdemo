## 1. 存储与管线（代码路径）

流水线：TextIn `detail[]` → `parse/textin.py::blocks_from_detail`（`type=table` 时 `cells[]` → `table_markdown()` 得 `content`，→ `table_html_from_cells()` 得 `table_html`；`content==1` 的页眉页脚项丢弃）→ `parse/chunker.py::chunk_document`（`keep_table_whole=True`：表格**永不切分**，整块成一个叶子）→ `parse/tree.py::build_tree`（表格**不挂父块**，`parent_block_id` 恒 NULL，`is_leaf=true`）→ `ingest/assets_docs.py::build_chunks_and_descriptions`（`describe_tables` 为**每张表**生成 `content_desc`，缺描述则 `validate_chunks` 整份文档回滚）→ `ingest/documents.py::_insert_blocks` 写库。

`core.doc_block` 中表格块的列：`block_type='table'`；`content`（Markdown，合并单元格展开成重复值）；`table_html`（迁移 010，保留 rowspan/colspan；**仅供未来"加总校验"用，不进检索**）；`content_desc`（一句话描述）；`page`（单个整数）；`bbox`（整张表一个归一化矩形）；`section_path`；`parse_confidence`（**块所在页**的页分，不是表格自己的分）；`chunking_version`；`embedding`/`embedding_version`。**没有**：单元格坐标、行列表头、单位、表标题、跨页信息、描述模型/提示词版本、来源引擎。

## 3. 数字溯源（对照 CLAUDE.md §0 / docs/05 §2.3 / docs/06）

- 现有可用的标识符：`block_id`、`page`（跨页表只有**首页**）、整表 `bbox`（跨页表是首段的框）、`content`/`table_html`。**没有单元格级标识**：没有 (row, col)、没有行表头/列表头标签、没有每格 bbox 与页码。
- 因此：回答能引用"[block_id | page]"到**整张表**，不能引用到"哪一行哪一列"。同一张表里出现 50 个数字，它们共用同一个溯源标识；验证器（尚未实现：`agents/` 下只有 prompts，`grep` 不到任何后置校验代码）即便实现，也只能做"数字是否出现在该块的文本里"这种弱检查，无法判定"数字是否取自正确的行/期"。
- 现状里唯一对表格单元格做语义取数的代码是 `ingest/stage2_crosscheck.py`（见 §4），它按 Markdown 行拆分字符串、取"第一格=科目名、同行里离目标值最近的数字"，并不知道哪一列是哪个期别。
- 缓存 JSON 的每个 cell 其实有**自己的 `page_id` 和 8 点 `position`**（104 张表的 6804 个 cell 全部有），信息在 JSON 里，入库时丢了。

## 4. 结构化事实路径

**表格不是结构化事实的来源。** `core.fin_fact`（1245 行）、`segment_revenue`（27）、`shareholder_holding`（190）全部 `source='wind'`，由 Wind 适配器直接写入（`ingest/facts_cli.py`、`facts_extras_cli.py`、`pit_tables.py`）。`fin_fact.source_block` 列存在（迁移 003，bigint）但 **1245 行全为 NULL**。
表格只用于**事后交叉核对**（`ingest/stage2_crosscheck.py`，只读）：
- 股东：同一行里有"同名且持股数逐股相等"的格；名字经 `normalise_name` 去空白/`<br>`/"(陆股通)"。
- 财务事实：`FACT_LABELS` 8 个科目，按"行首格 == 科目名"匹配，取同行与 Wind 值**最接近**的数字，容差 6000 元，返回页码。该逻辑对列不敏感（最接近原则可能取到相邻期的数；未做期别列校验），只能证明"Wind 值在原文某表某行附近出现过"。核对结果不落库。
结论：没有"表格 → 事实"的抽取链路，也没有把事实绑回具体 cell。若以后要从表格抽数（ADR/路线图里的 `eval_extraction`），必须先有 cell 级结构。

## 6. 检索效果

- 已有结果：`evals.eval_retrieval` 100 条合成用例（作者 `auto:deepseek-chat:v1`），其中 **29 条的 gold 是表格块**（70 条是段落块；gold 在现行文档上）。`evals.eval_run` 里 15 次运行（2026-09-30）只存**总体**指标：混合检索 R@10 0.75–0.81，R@50 0.91–0.92，MRR@10 0.61–0.65；**没有按块类型拆分**，所以"表格块在混合检索里表现如何"没有现成数字。文档 `docs/9.28-plan/验收记录/phase-7-阶段五-评测集与真实检索.md` 也没有表格专项分析。
- 我额外做了一个**纯库内的 BM25 单路对照**（免费、不调嵌入；用现有 `retrieval/lexical.py` 的 SQL，同 as_of/实体过滤，候选 50，当前库状态）：

| 子集 | 用例数 | 查 `content`（现行） R@10 / R@50 | 查 `content_desc` R@10 / R@50 |
|---|---|---|---|
| gold 为表格块 | 29 | **0.48 / 0.66** | 0.83 / 1.00 |
| gold 为段落块 | 71 | 0.89 / 0.99 | — |

  表格块词面召回明显低于段落（0.48 vs 0.89）。查 `content_desc` 高得多，但**这个对比有泄漏**：生成用例时（`evals/generate.py`）表格块的问题是看着"描述 + 正文"写出来的，问题天然贴近描述，不能当作"开 desc BM25 就能涨到 0.83"的证据，只能说明方向。混合检索有向量一路（embedding 含 desc），所以总体 R@10 比词面单路高。

## 7. 结论与提案

**总体判断**：解析面基本可用——数字召回面没发现系统性丢失，跨页表已被 TextIn 合并，描述器是真 LLM。但"表格"目前以**一张文本块**对待：数字溯源只到块，不到格；这与 CLAUDE.md §0"每个数字必须可溯源"的目标有差距，且对后续"从表格抽数/自动取数"是结构性阻塞。

### 新管线（分级路由：表格走 L1 PaddleOCR / L3 TextIn）的存表建议

目标：不管表格来自哪一级引擎，**落库形态统一为"带坐标的单元格网格"**，Markdown/HTML 只是派生视图。

建议结构（一张表一行 `core.doc_table`，外加 cell 明细；或 `doc_block.table_grid jsonb`，量小用 jsonb 更省事，查询需求出现再拆表）：

```
doc_table:
  block_id            -- 指向 doc_block（表块仍是检索单元，保持"不切分"）
  grid                -- jsonb: {rows, cols, cells:[{r,c,rs,cs,text,page,bbox,hdr?}]}
  pages               -- int[]（跨页表的全部页）
  caption / unit / currency / period_hint   -- §7 #4 的绑定结果
  source_engine       -- 'textin' | 'paddle' | 'l0'  + 引擎指纹
  verify_verdict      -- 'text_layer_closed' | 'dual_agree' | 'single_unverified' …（对应计划里 L1/L2 的 Verdict）
  verify_detail jsonb -- 数字闭合/表格行召回的数值，可复核
  provider_snapshot_ref -- 原始响应的 blob 路径（1.5 供应商可替换）
```

要点：
1. cell 级 `bbox` 归一化到页宽高（与现有 `_bbox` 一致），`page` 逐格存。
2. **引擎无关的归一化层**：PaddleOCR/TextIn/L0 的输出都转成同一个 `cells` 列表后再走 `table_markdown`/`table_html_from_cells`（这两个函数已有，输入是同样的 cells 形状）。
3. `verify_verdict` 必须随表落库——"单一引擎在无文字层页上的输出永远不采用"（路由计划）这一规则的结果，要能在引用时被看到。
4. 引用格式：`[block_id | page | r{row}c{col}]`，验证器按 `doc_table.grid` 取格，核对数值与单位。
5. 迁移：新表 + `asof` 视图（沿用 `asof.doc_block` 的做法，视图列只能追加）。

### 现有 52 份文档能否在**不再调用 TextIn**的前提下重建？

能。理由（已核实）：
- 缓存 JSON（`data/blob/parse/textin/<hash>/13c878f342724768.json`）`result.detail[]` 的 table 条目含：`cells[]`（每格：`row, col, row_span, col_span, text, type='cell', page_id, position[8 点]`）、`page_id`、`position`（整表 8 点）、`paragraph_id`、`sub_type`（bordered/borderless）、`caption_id`（50/104）、`split_section_page_ids`/`split_section_positions`（47/104，跨页）、`outline_level`。
- 现行 104 张表：**全部 cell 有自己的 page_id 与 position**；网格 0 空洞；所以 `(r, c, rs, cs, text, page, bbox)` 可 100% 重建。TextIn 没给的：`is_header`（需推断）、单元格置信度。
- `data/blob/parse/textin/` 的 JSON 与库里的 table 块逐张 1:1 对应（按文档内顺序，已验证 104 张全等）；更稳的做法是写入时同时记 `paragraph_id` 作为主键，避免依赖顺序。
