# 旧文档缓存重解析演练（2026-10-14）

## 一句话结论

按用户裁决改成"**逐块相同就只补元数据**"之后，在一份全新的演练副本上：可免费重解析的 73 份文档里，**72 份与现行块逐块相同**，只原地补了 `parse_source`、写了逐页台账和文档结论；块号、块内容、描述、嵌入、网格、时点列、评测题**一个字节都没变**（指纹比对一致），不需要改评测 gold。剩下 1 份（doc 266）与现行块不同，**原样保留旧切块**，不写台账，列为 `differs`。全程零外部调用、零付费，开发库 `ragdemo` 只被只读 `pg_dump` 过。

评测：重建 BM25 索引后，三套 C1 的 R@10 / R@50 与同一副本的"改前"**完全相等**；auto 的 MRR 差 0.0005，来自一道同分题的并列顺序（见 3.4）。**不重建索引时 auto R@10 会从 0.72 掉到 0.69**——原因是原地 UPDATE 在 BM25 索引里留下旧版本条目、改变了全局词频统计，VACUUM 不能消除，只有 REINDEX 能。所以真实库上的执行步骤里包含 REINDEX（第六节）。

## 一、做法

### 1.1 `ragdemo docs reparse-cached`（默认行为已改）

对每份现行、已有现行块、且 TextIn 缓存与 PDF 都在的文档，用新流程（`TieredParser`：整份 L3、不启用任何减页规则、L0 关闭；TextIn 走一碰就报错的重放传输层，blob 只读）重新解析并切块，然后与现行块**逐块比较**：数量、顺序（ordinal）、类型、内容、页码、章节路径、是否叶子、父块 ordinal 全部一致才算相同。

| 结局 | 条件 | 写什么 | 不动什么 |
|---|---|---|---|
| `filled`（dry run 显示 `fill`） | 逐块相同 | 原地补 `doc_block.parse_source`（新流程给了 `figure_meta` 时也补）；写 `core.parse_page_route` 与 `core.parse_doc_acceptance` | 块号、内容、描述、嵌入、`doc_table`、所有时点列、`document` 行、评测题 |
| `differs` | 有差异 | **什么都不写**，报告里写原因 | 全部 |
| `written`（dry run 显示 `replace`） | 有差异且加了 `--replace-differing`（默认关） | 取代旧版本、插入新块（描述 / 嵌入能沿用的沿用） | — |

- 选项：`--yes`（不加只 dry run）、`--doc-id`（可重复）、`--report <tsv>`、`--blob-root`、`--replace-differing`。
- 幂等：现行块全有 `parse_source`、且该解析产物已有文档结论的文档，再跑会列为 `already_new_flow` 跳过。
- `differs` 的原因（报告原文）：取代会让新旧两版在早于执行时刻的 `as_of` 上同时可见，检索出现重复（上一轮演练实测：auto R@10 0.72→0.59）。要替换，需先定好"重解析在过去时点如何呈现"，再用 `--replace-differing`。

### 1.2 只改这两列为什么不破坏时点不变量

- 迁移 `033_doc_block_parse_source_figure_meta.sql` 的说明：`parse_source` "只用于评测分组与审计，不参与检索打分"；两列"随 doc_block 既有时点列走，不登记 core.bitemporal_registry"。`core.doc_block` 本身在登记表里，但登记的时点公共列是 `valid_from / known_at / superseded_at / source / source_ref / ingest_run_id / ingested_at`（`ragdemo_core/db/invariants.py::BITEMPORAL_COLUMNS`），这次一列都没碰。
- `asof.doc_block` 的可见性只看 `known_at` / `superseded_at`，原地补元数据不改变任何 `as_of` 下看到哪些块；同样的原地补写已有先例（嵌入批处理原地写 `embedding`）。
- 演练副本上 `check_schema_invariants` 0 项违规。
- **一个副作用**：原地 UPDATE 会在 pg_search 的 BM25 索引里留下旧版本条目，影响全局词频统计，近似同分的块排序会变（见 3.4）。这不是时点问题，但会让评测数字漂移，所以执行后要 `REINDEX INDEX core.doc_block_bm25`。

### 1.3 其他代码（上一轮已提交，仍保留）

- `TieredParser.parse_periodic`：年报 / 季报整份 L3、`forced_l3`、带台账。
- `DocumentWriter.reparse_document(desc_provenance_by_ordinal=...)`：替换路径逐表沿用描述来源。
- `ragdemo docs remap-gold` 与 `scripts/remap_eval_gold.sh`：替换路径之后才需要的评测 gold 重映射；**默认模式不需要**（块号不变）。

### 3.4 评测（C1：`--models mock --no-rerank --w-vec 0`，同一副本）

| 时点 | auto R@10 / R@50 / MRR | 盲标表格 R@10 / R@50 / MRR | 盲标正文 R@10 / R@50 / MRR |
|---|---|---|---|
| 改前（恢复后的新索引） | 0.7200 / 0.8100 / 0.4875 | 0.3548 / 0.6129 / 0.1937 | 0.7714 / 0.8286 / 0.6260 |
| 补完元数据，未处理索引 | 0.6900 / 0.8000 / 0.4760 | 0.3548 / 0.6129 / 0.1928 | 0.7714 / 0.8429 / 0.6143 |
| 再 VACUUM | 同上（不变） | 同上 | 同上 |
| 再 `REINDEX INDEX core.doc_block_bm25` | **0.7200 / 0.8100** / 0.4880 | **0.3548 / 0.6129 / 0.1937** | **0.7714 / 0.8286 / 0.6260** |

- 未处理索引时的下降：块内容一字未变，但每个被 UPDATE 的块在 BM25 索引里多出一条旧版本条目，全局统计（文档数、词频）随之改变，近似同分的排序翻转（232 题里 49 题的名次有变化）。VACUUM 不清理 pg_search 索引里的这些条目；REINDEX 后统计恢复。这也解释了为什么开发库上记录的 B1-C1（0.68 / 0.3226 / 0.7571）低于任何一次新恢复的副本（0.72 / 0.3548 / 0.7714）：开发库索引早已积累了同类旧条目。
- REINDEX 后与改前仍有 3 题名次不同：q157 第 5→4 名（gold 是 5 份业绩预告里一模一样的套话，分数完全相同），q164、q186 在 14/15、24/25 名之间对调（都在前 10 之外）。原因：`retrieval/lexical.py` 的 BM25 排序只按分数排，没有并列时的决胜规则，同分块的先后取决于行在表里的物理位置，而 UPDATE 改变了物理位置。R@10、R@50 不受影响，auto MRR 因 q157 上升 0.0005。如要让评测在任何维护操作后逐题可复现，可以给 BM25 排序加 `block_id` 决胜（这是检索代码的改动，不在本任务范围）。

### 3.5 表格事实引用

默认模式不动 `doc_table`，`core.fact_table_ref` 的 48 条现行引用仍指向现行表（已核对 48/48），**不需要**重跑。`ragdemo facts table-check` 的 dry run 显示会写 59 条（48 + 11 条 `comparative_column`），多出的 11 条在任何改动前的副本上也一样，是该命令代码更新后一直没在库上重跑，和本次无关；要不要跑 `--yes` 另行决定。

### 3.6 运行时间

dry run 35 秒，`--yes` 55 秒（73 份）；REINDEX 数秒；每套 C1 评测 10–20 秒。

## 四、需要人决定的事

1. **doc 266 怎么办**：保持旧切块（现状，零风险）；或先定好"重解析在过去时点如何呈现"（上一轮报告的四个选项：检索层同版本组去重 / 旧版 `superseded_at` 贴近 `known_at` / 挪评测 `as_of` / 接受重复并重冻基线），再 `--replace-differing --doc-id 266`，之后用 `scripts/remap_eval_gold.sh` 改它的 10 个 gold 块（上一轮演练：4 个 overlap、0 丢失），并补 10 个块的嵌入（付费，极小）。
2. **真实库上要不要 REINDEX**：不 REINDEX，评测会随原地 UPDATE 漂移（演练里 auto R@10 −0.03），且漂移与本次改动无关、只是索引统计。REINDEX 后数字会变成"新索引口径"（演练副本口径：0.72 / 0.3548 / 0.7714，高于开发库现记录的 0.68 / 0.3226 / 0.7571），需要以 REINDEX 后的数字重新冻结基线。建议：执行前先 REINDEX 一次测"改前"，执行后再 REINDEX 一次测"改后"，两者应相等。
3. **5 份有缓存、从未切块的文档**（376、413、443、462、487）：仍不在范围，需付费描述或放宽校验，另议。
4. doc 576 第 6 页无输出告警，需人工查看。
