# 旧文档缓存重解析演练（2026-10-14）

## 一句话结论

能免费重解析的 73 份现行文档，已在**演练副本**上按新流程全部重写成功：零外部调用、零付费；表格描述 193 条全部沿用（不需要调模型）；嵌入 1641 个叶子块直接沿用，只有 10 个块需要重新嵌入；评测 gold 313 个块号全部找到了替身（0 个丢失）。

**但在真实库执行之前，有一件事必须先拍板（见第五节）**：重解析把旧块的 `superseded_at` 设为"执行时刻"，而三套评测题的 `as_of` 都早于执行时刻，所以在这些 `as_of` 上新旧两版块**同时可见**，检索结果里出现重复，C1 召回明显下降（auto R@10 0.72→0.59，改写 gold 之后）。只要"新旧两版不同时可见"，召回就回到原水平（模拟结果 0.71 / 0.3548 / 0.7714）。

开发库 `ragdemo` 全程**只读过一次**（`pg_dump` 取新备份），没有任何写入。

## 一、做了什么

1. **新命令** `ragdemo docs reparse-cached`（`packages/ragdemo/src/ragdemo/ingest/reparse_cached.py`）
   - 默认 dry run（不写库）；`--yes` 才写；`--doc-id` 可重复，限定范围；`--report` 输出逐文档 TSV。
   - 选择范围：现行、已有现行块的文档。缓存或 PDF 缺失的列出原因，原样不动。
   - 新流程 = `TieredParser`：整份 L3、不启用任何减页规则、L0 永远关闭。公告 / 研报走 `parse_for`；年报 / 季报（`annual_report` / `quarterly`）走新增的 `TieredParser.parse_periodic`（整份、`forced_l3`、带台账）；EDGAR 8-K 按公告路由。
   - 零外部调用的保证：TextIn 的传输层是 `ReplayTransport`，任何真实请求都抛错；blob 包一层只读（`ReadOnlyBlob`），写入即报错；表格描述只从旧现行块**内容逐字相同**时沿用，沿用不了的整份文档跳过并列出（本次 0 份）；嵌入只在"嵌入输入逐字节相同"时复制旧向量。
   - 写入走 `DocumentWriter.reparse_document`：旧文档 / 块 / 网格只标 `superseded_at`，不删；新块沿用旧文档的 `known_at`（发布时刻），不用 `ingested_at`。之后写逐页台账与文档结论（缓存命中，不写 provider_snapshot），更新公告目录指向。
   - 幂等：已在新流程上的文档（现行块全有 `parse_source`、且该解析产物已有验收结论）再跑会被跳过（`already_new_flow`）。
2. **`DocumentWriter`** 新增可选参数 `desc_provenance_by_ordinal`：每张表的描述来源（模型 / prompt 版本）按块分别记录，沿用旧描述时把旧 `doc_table.desc_model / desc_prompt_version` 带过来。不传时行为不变。
3. **gold 重映射** `ragdemo docs remap-gold`（`ingest/gold_remap.py`）与脚本 `scripts/remap_eval_gold.sh`：默认只读，输出报告 TSV 与待审 SQL。规则（确定性，不调模型）：
   - exact：同一文档现行后继版本里，去掉全部空白后内容完全相同的叶子块（多个时取同页、ordinal 最近）；
   - overlap：切块边界变了时，候选必须**同页**、且与旧块是包含关系（比较时去掉切块器加的"章节路径 + 换行"前缀），旧块文本被覆盖比例 ≥ 0.9；
   - lost：都不满足，旧块号原样保留，交人工。
   - SQL 是一个事务，带守卫：gold 必须仍等于生成时读到的值，否则整体报错回滚（重复执行不会二次改写）。
4. 测试：`tests/ingest/test_reparse_cached.py`（8 例）、`tests/ingest/test_gold_remap.py`（8 例）、`tests/ingest/test_documents.py` +1、`tests/parse/tiered/test_parser.py` +1，全部在隔离测试库上跑。没有新迁移。

## 五、评测：为什么召回变了（每一处都已解释）

口径一律 C1：`--models mock --no-rerank --w-vec 0`。

| 场景 | auto R@10 | 盲标表格 R@10 | 盲标正文 R@10 |
|---|---|---|---|
| ① 开发库上的记录（B1-C1，今天 03:52） | 0.6800 | 0.3226 | 0.7571 |
| ② 演练副本，重解析前 | 0.7200 | 0.3548 | 0.7714 |
| ③ 重解析后，gold 未改 | 0.6500 | 0.2742 | 0.7429 |
| ④ 重解析后，gold 已重映射 | 0.5900 | 0.1935 | 0.6714 |
| ⑤ 模拟：只有新版可见 | 0.7100 | 0.3387 | 0.7714 |
| ⑥ 模拟：只有新版可见 + 重建 BM25 索引 | 0.7100 | 0.3548 | 0.7714 |

- **①→②（同一份数据、同一份代码，召回不同）**：恢复备份会从头重建 BM25（tantivy）索引；开发库的索引经过多次更新，残留的旧版本行仍参与词频统计，近似同分的块排序因此不同。所以对比只能在同一个库、同一索引状态下做，②才是本次的"改前"。
- **②→③、④（下降）**：评测题的 `as_of` 分别是 09-30、10-14 01:39、10-14 03:36，都早于重解析时刻（10-14 04:21）。按现行谓词，旧块 `superseded_at`（04:21）晚于这些 `as_of`，**仍然可见**；新块 `known_at` 沿用发布时刻，**也可见**。同一段文字出现两份，前 10 名被重复项挤掉一半；gold 改成新块号后，旧副本块号更小、同分排在前面，MRR 掉得更厉害（auto MRR 0.4875→0.2019）。这正是 `retrieval/expand.py` 注释里提到的"新版继承过去的 known_at、旧版 superseded_at=now()，中间时点两版都可见"，只是这次发生在块上、而且正好落在评测时点。
- **⑤（只有新版可见时基本回到原值）**：在一次性副本上把本次被取代的旧块 / 网格 / 文档的 `superseded_at` 改成 `known_at + 1 微秒`（仅为测量，不是建议的做法），再改好 gold。剩下的差别：
  - auto 少 1 题（q_id 115，第 10 名与第 11 名对调）：两块分数几乎相同，doc 266 少了 25 块，全语料的 BM25 统计（总块数、平均长度）随之变化，近似同分的顺序翻转；块集合完全一样。另有 4 题名次小幅移动（q108 属于 doc 266，因切块变了；q151/152/157 的 gold 是多份公告里相同的套话，同分块按块号决胜，新块号顺序变了），均不影响 R@10。
  - 盲标表格 0.3387：重建索引后（⑥）回到 0.3548，与②完全一致，差别来自索引里的旧版本行。
  - 盲标正文：与②相同（R@50 由 0.8286 升到 0.8429，多 1 题）。

**需要先拍板的事**：在真实库执行之前，必须决定"重解析（同一份原文换解析结果）"在过去时点上怎么呈现。可选：

1. **检索层去重**：同一 `version_group` 在 `as_of` 时点有多个版本都可见、且 `known_at` 相同时，只取最新版本（与 `expand.py` 对网格"取最大 table_id"同一思路）。不改历史数据，但要改检索与 asof 视图口径，需要 ADR。
2. **重解析时把旧版的 `superseded_at` 设成紧贴 `known_at`**（即"新解析结果从原文发布起就视为有效"）：模拟结果就是⑤。这等于改写"过去某时刻系统展示了什么"，违背现在 `superseded_at = 取代时刻` 的约定，需要 ADR。
3. **不改语义，把三套评测题的 `as_of` 挪到重解析之后**：盲标两套挪到执行时刻之后，可见语料不变（10-14 01:39 之后没有新文档）；但 auto 题挪到现在会多出 299 个 09-30 之后才可知的叶子块，等于换了题集，需要重新冻结基线。
4. 什么都不改，接受过去时点上两版并存，重新冻结三套基线（召回数字会明显变低，且不代表检索真实变差）。

我的建议是 1（不动历史数据，与网格的既有处理一致），但这是设计决定，本任务没有替你做。

## 八、回滚

重解析不写 blob，回滚只需恢复数据库：

```bash
docker exec ragdemo-db psql -U postgres -d postgres -c \
  "SELECT pg_terminate_backend(pid) FROM pg_stat_activity WHERE datname='ragdemo' AND pid<>pg_backend_pid()"
docker exec ragdemo-db dropdb -U postgres ragdemo
docker exec ragdemo-db createdb -U postgres ragdemo
docker exec -i ragdemo-db pg_restore -U postgres -d ragdemo < data/export/ragdemo-pre-reparse-cached-$TS.dump
# 预期只有 3 条可忽略的报错：schema paradedb / tiger / topology already exists
```

只想撤掉 gold 改写而保留重解析：gold 改写前后的块号对照在 `gold-remap.tsv` 里，反向生成一份 SQL 即可；`evals.eval_retrieval` 是原地更新、没有版本历史，所以 gold 回滚只能靠这份报告或备份。
