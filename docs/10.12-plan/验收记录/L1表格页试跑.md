# L1（自托管 PaddleOCR）表格页试跑

日期：2026-10-13。只测量，不改生产模块。脚本 `scripts/l1_pilot.py`（`select` / `run` / `analyze`），纯函数单测 `tests/parse/tiered/test_l1_pilot.py`（12 条）。
未调用任何付费接口（TextIn / LLM）；库与 blob 只读；一次一页串行；没有启停、重建任何容器，`docker restart` 一次也没有执行。
原始数据在 `data/experiments/l1-pilot/`（gitignored：`sample.tsv`、`ref/`、`md/`、`results.jsonl`、`analysis.json`）。

## 1. 结论（先看这里）

1. **L1 严格通过率 = 0/37（Wilson 95% [0.00, 0.09]）。** v8 的 `verify_against_text_layer` 一页都没放行。
2. 失败几乎全是**校验口径与引擎输出形态的结构性冲突**，不是随机 OCR 错误：
   - 31/37 页触发"数字/文字顺序与文字层不一致"与"表格结构"（空单元格 25 页、rowspan/colspan 18 页、行宽不一 18 页）。v8 对 L1 页**禁止**空单元格、合并单元格、行宽不齐；真实公告表格里这三样很常见。
   - 顺序不一致的一个已核实原因（样本 6，逐 token 对比）：文字层把被换行的标签的后半句（"常性损益的净利／润"）排在该行数字**之后**，而引擎按单元格输出，标签完整排在数字之前；另有 "%" 与 "第二/三/四" 的位置差。同类原因在其它页是否同样占多数，**只逐 token 核实了这一页**，其余页是按标签推断。
   - 6/37 页引擎吐出结构错误的 HTML（`</table>` 不配对、表内单元格外有文字、`tbody` 未闭合）。
   - 12 页有丢失数字、8 页有凭空数字（典型：长数字被拆成两段，如 `2162612869.80` → `2162612` + `86.80`；`137600000` → `00`/`000`）。
3. 若把"顺序"与"表格结构"两条拿掉（**仅诊断，不是门槛**），其余校验 + 网格可转换的页数为 15/37 = 0.405（Wilson [0.26, 0.57]）。这是上界，不是可发布的通过率。
4. **成本：按测得通过率 0，混合成本 = 0.1356 元/页，与全走 TextIn 相同；0.05 元/页不可达。** 即使通过率取 Wilson 上界 0.094，也只有 0.125。
5. **耗时与稳定性**：均值 49.9 s/页（中位 47.1，p95 71.9，最大 103.8），约 72 页/小时；38 次调用 0 次 OOM、RestartCount 始终 0，峰值内存 12.08 GiB（`mem_limit` 13 GiB，余量约 0.9 GiB）。**但该容器空闲约 23 小时后的第一次调用耗时约 1 小时才返回**（见 §4.3），这一点必须在批处理设计里处理。

## 2. 样本（与任务要求的偏差）

- 来源：`docs/10.12-plan/l0v2/split.tsv` 中 `group=docs、set=tune` 的 14 份文档，全部有 TextIn 缓存解析；没有碰 holdout / holdout2。种子 20261020。
- 页：页型（census 代理）为 table 或 financial_statement，且 TextIn 缓存在该页有表格（参考网格）。
- **候选页只有 37 页，不足 40。** 调参集的 14 份文档总共才 71 页，其中符合条件的就是这 37 页；没有放宽到留出集，所以样本是 **37 页，不是 40**，分层只是"能抽到的都抽"。announcement 层文档只有 21 页符合，所以补入了同一调参集里的 annual_report（546）与 quarterly（547、548）文档的 16 页。另：文档 565 的 `doc_type` 是 announcement，但内容是年报摘要式的 12 页（含三张报表页）。
- 分层（标签由文字层与参考网格启发式给出）：key_figures 12、other_table 13、multi_table 6、balance_sheet 2、income_statement 2、cash_flow 2；**multi_row_header 与 small_table 两层为 0 页**（调参集里没有）。
- 页之间不独立（同一文档的相邻页占大头：548 与 565 各 11 页），所以 Wilson 区间**偏乐观**。
- 参考网格：TextIn 跨页表格（报表页大多如此）按单元格自带页码切出落在该页的部分，行号重排、rowspan 截到本页；这类参考是"半张表"，形状比较对它们天然不利（样本里 21 张）。
- TextIn 参考本身并不是真值：多处差异是 TextIn 侧的（如 "增加1 .95个百分点" 被拆成 1 与 95），见 §5。

## 4. 运行、内存与耗时

### 4.1 吞吐与积压小时数
均值 49.9 s/页（含大部分表格页与三类报表页），72 页/小时。积压的 L1 页数按 census 比例外推（公告去重后 6445 页，非定期占比取 0.68，研报 596 页；比例来自 `全量解析盘点.md` §6 的普查，粗代理）：

| 场景 | L1 页数 | 小时 | 对照"≤ 40 小时" |
|---|---|---|---|
| L0 关闭，所有有文字层的非报表页都走 L1 | 约 4042 | 约 56.0 | **超** |
| L0 开启，仅表格 + 多栏页走 L1 | 约 1401 | 约 19.4 | 过 |
| 仅表格页（本次测的页型） | 约 897 | 约 12.4 | 过 |

注意：L0 关闭时 L1 要承担纯文字页，纯文字页的 L1 通过率本次**没有测**（样本全是表格页）。

### 4.2 稳定性
- 38 次调用（含重跑的第 1 页）0 次 OOM、0 次重启；runner 的"连续 3 页被杀 / 超过 180 s 即停"从未触发。
- 峰值 12.08 GiB，距 13 GiB 上限约 0.9 GiB；`docker stats` 每次约 2–4 秒，真实峰值可能更高。
- runner 逐页追加 `results.jsonl`，已完成的页重跑时跳过，即可断点续跑（这满足裁决里"可续跑"的要求，但这只是本次测量脚本，不是生产批处理器）。

### 4.3 冷启动异常（需要工程处理）
容器空闲约 23 小时后的**第一次**调用（样本 1，文档 266 第 2 页）：客户端 180 s 超时，之后引擎仍在满负荷计算（CPU 1200–1900%，峰值内存先停在 1.5 GiB 再一路涨到 11 GiB 以上）；单线程薄壳在这期间对 `/v1/health` 也不响应（20 s 超时）。约 1 小时后引擎才恢复空闲（精确结束时刻未捕获，起点约在 05:3x UTC、06:32 UTC 已恢复）。之后同一页重跑：51.7 s、峰值 11.74 GiB，成功。结论：不是该页的问题；原因（模型懒加载、首次推理编译等）**未查清**。后果：
- 150 秒级的 HTTP 超时对冷启动无意义，而且客户端超时**不能取消**引擎里的计算，下一个请求会排在后面。
- 批处理前应发一次不计入统计的预热请求；`HttpPageEngine` 的 180 s 超时与"页失败即降级到 TextIn"的逻辑在引擎被占住时会连锁失败。
- 本次 runner 对此的处理：超时后等健康检查恢复（最长 45 分钟），并如实记录。

## 5. 失败样例（数字层面）

- 引擎把长数字拆开：`2162612869.80` → `2162612` 与 `86.80`；`14376889476.95` → `14376889` 与 `47.95`；`4033794964.38` → `4033794` 与 `94.38`。这是真正的引擎错误，v8 的闭合校验会拦（丢失 + 凭空）。
- `137600000`（文字层）→ 引擎出 `00`、`000`：同类。
- TextIn 参考侧的问题（不是引擎错误）：`增加1 .95个百分点` 在 TextIn 里数字被拆成 `1`、`95`，引擎得到 `1.95`；表格里 `0.52` 同样。这使"数字召回 vs TextIn"被低估，因此同时报了对文字层的数字召回（0.986）。
- 表数不一致的页：样本 9、20、21、26 引擎只输出 1 张表而参考有 2 张（按顺序配对后其余指标失配）；样本 23 的 HTML 结构错误导致无法转网格。

## 6. 混合成本（路由计划 T7 `CostInputs` 公式，L0 关闭、L1 开启、L2 关闭，c_local = 0，c_textin = 0.1356）

公式原样实现在 `blended_cost`（有单测）。census 输入：公告 `scan_share` 0.182、`statement_share` 0.011；研报 0.012、0.153；路由范围合计 0.162、0.031（`全量解析盘点.md` §6）。

l1_pass 对所有"有文字层的非报表页"一律取同一个值（保守假设：本次只测了表格页）。

| l1_pass | 公告 | 研报 | 路由范围合计 |
|---|---|---|---|
| 测得 0/37 = 0.000 | 0.1356 | 0.1356 | 0.1356 |
| Wilson 下端 0.000 | 0.1356 | 0.1356 | 0.1356 |
| Wilson 上端 0.094 | 0.1253 | 0.1249 | 0.1252 |
| 诊断（去掉顺序与结构两条）0.405 | 0.091 | 0.090 | 0.091 |
| 诊断的 Wilson 区间 [0.26, 0.57] | 0.107 – 0.074 | 0.106 – 0.071 | 0.107 – 0.073 |
| l1_pass = 1.0（理论下界） | 0.026 | 0.022 | 0.026 |

**0.05 元/页是否可达：**
- 在本次测得的 L1（v8 原样口径）下不可达：成本等于全走 TextIn。
- L0 关闭时，达到 0.05 需要 L1 通过率 ≥ 约 0.78（公告 0.78、研报 0.75、合计 0.78）；风险评估 §3.1 里"盈亏点约 0.5"是 **L0 开启**（纯文字页由 L0 承担）时的口径，二者不矛盾，但 L0 关闭时门槛更高。
- 即使放宽到上面的诊断通过率 0.405（Wilson 上端 0.57），L0 关闭时也到不了 0.05（0.073–0.091）。
- 一个更贴近现实的边界：公告里表格页（census 616/4348）按本次结果 L1 全失败、其余页 L1 全部通过（上界），成本 0.045；若其余页 L1 通过 0.7，则 0.072。也就是说，**0.05 只在"表格页以外的页 L1 几乎全过"时才擦边**，而这件事本次没有测。

## 8. 局限与需要后续核实

1. 样本 37 页、调参集内 3 份文档占大头，区间偏乐观；没有 multi_row_header 与 small_table 两层；16/37 页来自年报/季报类文档，这类文档在路由计划里本就整份走 TextIn。
2. 参考网格（TextIn）不是真值；grid_exact 与"数字召回 vs TextIn"受 TextIn 自身错误与跨页切分影响。更可信的是对文字层的指标。
3. 顺序不一致的根因只在一页上逐 token 核实过。"label 换行导致文字层顺序与单元格顺序不同"是否普遍、能否用更宽容的校验口径安全地吸收，需要单独评估；**放宽 v8 校验会削弱"数字错位也要拦住"的保证，不能因为本次通过率为 0 就直接放宽**。
4. 纯文字页与多栏页的 L1 通过率没有测。
5. 冷启动原因未查清（§4.3）。
6. 许可证仍未核查（T5 记录 §7.4）。
