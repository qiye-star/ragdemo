# 向量保底进重排评测（2026-10-14）

## 1. 要解决什么

改了重排输入（`rerank_rich_input`）之后，表格题 R@10 的天花板是“gold 有没有进重排的 50 个候选”：盲标表格题 R@50 = 0.85，自动题 R@50 = 0.88。没进候选的题分两类（见 `表格题检索失败分析.md`、`重排输入改造评测.md` §4）：

- 向量一路其实找到了（前 10 名左右），但 BM25 权重 0.6 的加权 RRF 把只被向量命中的块挤出了融合前 50，根本到不了重排。自动题里是 149（向量第 13）、179（向量第 10）。
- 两路都没找到：118、148。这一类本改动管不了。

## 2. 改了什么

- 新增配置 `RetrievalConfig.rerank_vector_guarantee: int = 0`（**默认 0 = 关闭**，行为与之前完全一致）。设为 N 时，向量一路的前 N 名一定会送进重排。
- **候选总数不变**，仍是 `fusion_k`（50）。不在融合结果里的保底块追加到末尾（按向量名次），为它们腾位置时从融合结果尾部挤掉**不属于保底**的块；已在融合结果里的保底块原位不动。所以重排一次处理的文档数不变，成本不变。
- 只在重排开启时生效；重排关闭时仍直接截断融合顺序。重排超时或失败降级时，回退顺序就是这份候选的顺序（保底块在末尾，基本不影响回退结果的前 10）。
- 只对主查询的向量结果保底；查询改写的变体不保底（改写默认关闭）。
- 实现：`retrieval/fusion.py::guarantee_vector_top`（纯函数）、`retrieval/service.py`。取值校验：0 ≤ N ≤ fusion_k。
- 诊断：`RetrievalTrace.rerank_candidates` 记下实际送进重排的候选；`eval run` 的逐题记录新增 `cand_rank`（gold 在重排候选里的位置，没进为空），命令行输出多一行“gold 进重排候选 x/n”。
- 评测参数：`eval run --rerank-vector-guarantee N`，值随 config 写进 `eval_run.config`。
- 没有迁移，没有改 prompt、切块、模型。测试先写后实现（新增 12 条，先失败后通过）；tests/retrieval 与 tests/evals 共 208 条通过；改动文件 ruff 与 mypy --strict 通过。

**注意 R@50 的口径**：`eval run` 的 R@50 是“不开重排时融合前 50”的召回，保底只作用于重排候选，所以 R@50 按定义不会变。保底的作用要看“gold 进重排候选”这一项。

## 3. 评测（C2：siliconflow 嵌入+重排，pgvector，默认 rich input 开、超时 3 秒）

预先约定的规则：盲标表格题 R@10 提升 ≥ +0.02，**且**两套题任何分组 R@10 下降不超过 0.02，**且** other/auto MRR@10 下降不超过 0.02，**且** p95 延迟增加不超过 30%。四条全满足才建议打开。付费 C2 上限 4 次，用了 4 次，按“基线、N=10”成对、同一时段跑。

## 4. 为什么不过，以及机制本身有没有用

两条不过都和重排接口当时不稳定有关，而不是保底规则做坏了什么：

1. **盲标集被超时淹没。** 盲标两次运行分别有 14 题、16 题重排超时（3 秒）后回退到融合顺序，而且是不同的题。逐题看，N=10 那次“新丢”的 5 题（242、244、256、260、261）全部是这次超时、基线那次没超时；“新中”的 6 题里 4 题（201、205、207、232）是基线那次超时、这次没超时。只看两次都没超时的 32 题：R@10 0.8438 → 0.9062，MRR 0.6592 → 0.7190。但这不是预先约定的口径，只能当参考。
2. **自动题 p95 变差的原因不能确定。** 重排文档数没变（都是 50），重排耗时 p95 从 1012 ms 到 2356 ms。可能是接口波动（同一时段盲标基线的 p50 已经到 2.8 秒），也可能是被换进来的保底块多为较长的表格块、使重排输入变长。只有一次运行，分不开。

保底规则本身确实把“融合截断”的题救了回来，而且没有一题因为保底被挤掉：

| 题 | 集合 | 向量名次 | 基线 | N=10 |
|---|---|---|---|---|
| 179 | 自动 | 10 | 没进候选，未命中 | 进候选（第 50），**最终第 3** |
| 149 | 自动 | 13 | 没进候选 | 没进（向量第 13 超出 N=10） |
| 118、148 | 自动 | 两路都没召回 | 未命中 | 未命中（本改动管不了） |
| 213 | 盲标 | 9 | 没进候选，未命中 | 进候选，**最终第 1** |
| 233 | 盲标 | 9 | 没进候选，未命中 | 进候选，**最终第 1** |
| 217、238 | 盲标 | 18、13 | 没进候选 | 没进（超出 N=10） |

也就是说，被保底送进重排的 3 题全部排进了前 10（其中两题第 1）。自动题 other/auto 指标逐位不变，说明为保底腾位置时挤掉的融合尾部块对结果没有影响。

## 5. 建议

- 按规则：**保持关闭**（`rerank_vector_guarantee = 0`）。
- 机制有效（3/3 救回），不过的原因是测量被重排接口超时干扰，加上一次无法解释的 p95 上升。如果要再判，建议在接口稳定的时段把同样四次运行重跑一遍（需要新的付费额度，本次 4 次已用完），并看逐题 `ms_rerank` 确认 p95 是否和换进来的表格块长度有关。
- N 的取值：149、217、238 的向量名次在 13–18，N=10 够不到；但不建议为这几道题去调 N，那是对着失败题调参。

## 6. 花费

付费 C2 共 4 次（自动题 100 题 ×2、盲标 62 题 ×2；每题 1 次嵌入 + 1 次重排，R@50 的宽检索不走重排）。无 TextIn、无 LLM 生成调用。
