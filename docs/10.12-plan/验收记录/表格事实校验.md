## 1. 口径（相对简报的收紧，均为评审后约束）

- 只用 `check == "match"` 且有页码与 bbox、跨度 1×1、整格恰一个金额的单元格；`cell_value` 为 None 的格不参与。
- 列：`parse_period_path` 必须恰好等于 `PeriodRef(报告期, 期望口径)`；流量 `ytd`，时点 `point`；`col_header_path(..., row=r)` 为 None（重复子表头之下）不用。
- 同一行上同一 `PeriodRef` 的列 ≥ 2（调整前/后、并列"本报告期"…）→ `ambiguous/duplicate_period_column`；唯一一列带"调整前/调整后/重述/预计/预测…"限定词 → `ambiguous/qualified_period_column`。
- 现金流量表里 `single_quarter` 口径的列不采信（由 `statements.py` 报表类型裁决）。
- 母公司：caption 含"母公司"的表、表头含"母公司"的列永不作为合并口径事实的佐证（只有母公司表有该科目 → `no_row/parent_company_only`）。
- 非日历财年：Q1 判定要求 `TableView.calendar_fy is True`（加载器仅对 `CN.` 实体置 True），缺标记 → `ambiguous/fiscal_year_flag_missing`。
- 单位：`TableContext.unit_for_cell`（行内 > 列 > 表）；不在 `UNIT_SCALE` → `no_unit`；表币种不在 (None, CNY) → `not_cny`；`--strict-unit` 不采信 `preceding_block` 的表单位。
- 只在别的期别的报告里作为比较列出现、且数值对不上的（可能是追溯调整后的数）→ `ambiguous/comparative_mismatch_possible_restatement`，**不记 mismatch、不落库**。`mismatch` 只来自事实自己那期报告的表（`own_document`）。
- 数值比较全部是 Python `Decimal`；容差 `max(6000, 0.5×10^-小数位×倍数)`；DB CHECK 让"超容差标 match"不可能写入。

## 5. 覆盖不足的原因（诊断，未修）

`no_period_column` 136 条（占 CN.688041/CN.000977 两个实体 191 条事实的 71%）不是匹配逻辑拒绝，而是 T17 `parse_period_path` 对下列真实表头返回 None（本任务不改 `periods.py`，列为后续项）：

1. 年报"主要会计数据"表的裸年份列头 `2025 年 / 2024 年`（未带"度"）：`_YEAR_ONLY` 只认"YYYY年度"。
2. 三季报利润表/现金流量表的 `2025 年前三季度 (1-9 月)`：括号里的"1-9 月"使残余文字判含糊。
3. H1 的"主要会计数据"表有两段（先"本报告期末/上年度末"，再"本报告期/上年同期"）：第二段表头在表体里被识别为重复子表头，`col_header_path(row=r)` 返回 None（T4 的保守设计：宁可没有）。
4. 同表出现两个并列"本报告期"列（表 494 的 2024Q1）→ 重复期别，按规则不采信。

修了 1–3 能显著提高覆盖，但应走 T17 的评审/测试流程（并重跑本检查）。
