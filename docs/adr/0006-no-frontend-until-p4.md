# ADR-0006 · P1–P3 不做 Web 前端

- 状态：已接受
- 日期：2026-09-21
- 决策者：创始团队

## 背景

简报 §12 第 5 问：起步是否需要 Web 前端，还是先用 Markdown 邮件/飞书推送简报。

团队构成是 2–3 位金融背景创始人 + 1 位待招的技术负责人
（前期外包过渡）+ 0–1 位数据工程师（`00-overview.md` §3）。
前 16 周（P1–P3）的工程人力极其有限。

## 备选方案

**A. P1–P3 无前端**：CLI + Markdown/HTML 简报 + 邮件/飞书机器人推送，P4 再上 Web。

**B. P1 就做最小 Web**：FastAPI + 极简页面，很早就能点击溯源、人工标注、录评测集。

**C. 只出 API，不做推送**：提供 REST 接口，创始人自行调用。

## 决策

**选 A。**

方案 B 的理由是真实的——标注效率确实是瓶颈，P1 要录 100 条 `eval_retrieval`、
P2 要录 50 条 `eval_extraction`，在 CLI 里做这些事很痛苦。但前 16 周的工程量
必须投到数据质量与评测上：如果检索召回率不达标、时点机制有漏洞，
再好的界面也只是把错误答案展示得更漂亮。

方案 C 被否决是因为它没有「每日自动产出」的节奏。P3 的验收标准是
「连续 2 周每日自动产出事件解读与观点」，这需要推送作为交付通道。
没有推送，产出就只是数据库里的行，没人会每天去看。

## 缓解：标注工具用 CLI 但要认真做

否决方案 B 的代价是标注效率。缓解方式是**把 CLI 标注工具当正经工具做**，
而不是随便写个脚本：

```bash
ragdemo eval add-retrieval --question "..." --as-of 2024-08-01
# 交互式：展示检索结果，方向键选中正确的块，回车标记 gold

ragdemo opinion review --pending
# 逐条展示待确认观点、依据链、原文摘录，y/n/e 确认/拒绝/编辑

ragdemo score evidence --due
# 展示到期观点与检索到的新证据，输入 -2..2 打论据分
```

这三个命令分别服务 P1、P3、P3 的关键流程。它们的开发量远小于 Web 前端，
但能消除大部分标注痛苦。

## 后果

1. **P1–P3 的交付形态**：Markdown / HTML 简报，经邮件或飞书机器人推送。
   溯源通过文内引用标注 + 附录原文块实现（`10-roadmap.md` P2 验收项），
   不需要点击。
2. **P2 的「每个数字可点回原文」验收项**在无前端条件下的含义是：
   每个数字带 `[block_id | page]` 标注，且简报附录包含对应原文，
   人工可以核对。P4 上 Web 后才是真正的「点击」。
3. **`src/api/` 在 P4 才开始写**。P1–P3 的所有入口都是 CLI，
   这也让自动化与人工操作走同一条代码路径，减少两套实现的不一致。
4. **HTML 渲染从 P2 就要做**（不只 Markdown）：飞书与邮件对 Markdown 的
   渲染差异很大，表格尤其容易乱。HTML 模板同时也是 P4 Web 页面的起点。

## 推翻条件

- 标注效率被证明是进度瓶颈（表现为：评测集录入耗时超过对应阶段总工时的 20%）
  → 提前做最小标注 Web 界面，但仍不做面向用户的产品前端；
- 出现需要早期用户反馈的商业机会，且反馈必须通过界面收集；
- 技术负责人到位且有前端能力富余——但即便如此，也应先问「前端是不是
  当前最该做的事」，而不是因为有人力就做。
