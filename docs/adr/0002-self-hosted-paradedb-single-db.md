# ADR-0002 · 自建 ParadeDB 单库，不用托管 RDS

- 状态：已接受
- 日期：2026-09-21
- 决策者：创始团队

## 背景

[ADR-0001](0001-bm25-paradedb-pg-search.md) 选择了 `pg_search`，而阿里云/腾讯云的
托管 RDS PostgreSQL 不允许安装第三方扩展。数据库形态因此必须重新决定。

同时，简报 §9 的 P6 要求支持私有化部署。私有化时点是否影响 P1 的架构选择，
是简报 §12 的开放问题之一——本 ADR 一并回答。

## 备选方案

**A. 自建 ParadeDB 单库**
云主机上跑 ParadeDB 官方镜像（自带 `pg_search` + `pgvector`），docker-compose 编排全栈。
事实表、向量、BM25 索引全在一个库、一个事务里。

**B. 混合：托管 RDS + 自建检索库**
托管 RDS 存 `entity` / `fin_fact` / `opinion` 等结构化数据（享受自动备份与高可用），
自建 ParadeDB 只存 `doc_block` 做检索。

**C. 回到托管 RDS + `zhparser`**
推翻 ADR-0001，换取托管的运维便利。

## 决策

**选 A。**

方案 B 看似两全，实际是最差的：`06-retrieval.md` §4.2 的检索 SQL 需要同时用到
`doc_block` 的向量、BM25、以及 `known_at`/`entity_id` 过滤，跨库后
`known_at <= as_of` 的过滤必须在应用层分两段完成——先在检索库拿候选，
再回结构化库校验。这正是 ADR-0001 拒绝方案 C（外置索引）的同一个理由，
换个形式又回来了。

方案 C 是推翻上一个决策，不在本 ADR 的讨论范围（它的触发条件写在 ADR-0001 的
「推翻条件」里）。

## 后果

### 正面

1. **时点一致性最强**：所有过滤在同一个 WHERE 子句里，
   `asof` schema 视图机制（`03-point-in-time.md` §4）能覆盖全部数据。
2. **P1 即是可私有化架构**。这直接回答了简报 §12 的第 7 问：
   私有化不影响 P1 的架构选择，因为 P1 用的就是可私有化的形态。
   P6 需要补的只是许可证管理与离线模型端点，不需要重构。
3. **不绑定云厂商**。全栈 docker-compose，换云或下云都是搬容器。
4. **成本更低**：同等规格下云主机比托管 RDS 便宜，对 5000 元/月的预算有意义。

### 负面（必须正视）

1. **备份要自己做**。托管 RDS 的自动备份、PITR、跨可用区副本全部消失。
   必须建：每日 `pg_dump` 到对象存储（保留 30 天）+ WAL 归档 PITR +
   **每月一次恢复演练**。恢复 runbook 是 P1 的验收项（`10-roadmap.md`）。
2. **监控要自己做**：连接数、慢查询、磁盘水位、复制延迟、向量索引构建耗时。
3. **没有开箱即用的高可用**。起步期接受单点——单机故障恢复时间以小时计，
   对研究工具可接受，但要写进 SLA 预期。用户增长后再上流复制。
4. **升级要自己做**。PostgreSQL 大版本升级、ParadeDB 版本升级都要自己规划与演练。

这四条是真实成本，不是「以后再说」。P1 验收里放了备份恢复演练，
就是为了让这笔成本在第一阶段就被支付而不是被推迟。

## 推翻条件

- 托管 RDS 开始支持 `pg_search`（则迁回托管，获得备份与高可用）；
- 运维负担被证明超出团队承受能力（表现为：数据库相关的事故或运维工时
  持续占用超过技术人力的 20%）；
- 用户规模要求高可用 SLA，而自建的故障恢复时间不可接受；
- 数据量超过单机合理承载，需要读写分离或分片——届时的架构变更幅度远超本 ADR，
  应写新 ADR 而非修改本篇。
