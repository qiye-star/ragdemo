# ADR-0005 · 公告数据源先定接口、不锁定供应商

- 状态：已接受
- 日期：2026-09-21
- 决策者：创始团队

## 背景

A 股 / 港股公告是本系统最核心的语料。简报明确「不自建爬虫，公告走供应商接口」，
候选包括庖丁 PDFlux、通联数据、同花顺 iFinD 等，但尚未选定
（简报 §12 第 1 问）。

问题在于：公告适配器（L5）是 P1 的关键路径，而供应商选型涉及采购、
商务谈判与试用，时间不可控。如果 P1 等待选型结果，整个进度会被阻塞。

## 备选方案

**A. 先定接口、不定供应商**
定义统一的归一化模型（`NormalizedDocument` / `NormalizedBlock`）与
`AnnouncementProvider` 协议，配 Mock 实现与契约测试集。选定后只需写一个 adapter。

**B. 先按某一家（如 PDFlux）的返回结构写具体实现**
以该供应商的数据模型为主模型，其他供应商后续适配。

**C. 不用供应商，自己用 MinerU 解析交易所 PDF**

## 决策

**选 A。**

方案 B 的问题不是「可能换供应商」，而是**主模型会被某一家的实现细节污染**：
如果按 PDFlux 的结构定义 `doc_block`，那么它对章节层级的表达方式、
表格的序列化格式、页码的语义都会渗进数据库 schema 与检索逻辑。
换供应商时受影响的就不只是 adapter，而是整条管线。

方案 C 与简报的「不自建爬虫」约束冲突，且通用解析对中文公告的表格结构还原
与章节识别准确率明显低于专业供应商——而这两项直接决定检索质量
（`05-document-pipeline.md` §1）。它保留为**兜底路径**（供应商未覆盖的文档），
不是主路径。

## 决策内容

P1 交付：

1. `NormalizedDocument` / `NormalizedBlock` 归一化模型（`04-ingestion.md` §2.3）——
   这是主模型，由我们的检索需求定义，不由任何供应商定义；
2. `AnnouncementProvider` 协议；
3. Mock 实现（`src/adapters/mock/`），**是一等公民不是测试脚手架**——
   P1 整条管线靠它跑通；
4. 契约测试集（`tests/contracts/`），选定供应商后新 adapter 必须全部通过；
5. **供应商评估清单**（`04-ingestion.md` §2.3 的六项能力），
   作为采购谈判的技术附件。

## 后果

1. **P1 不被采购阻塞**。下游（切块、嵌入、检索、评测）全部可以基于 Mock 推进。
2. **选型有了客观标准**。六项能力清单 + 契约测试集把「哪家好」从主观判断
   变成可核对的清单，谈判时也更有底气。
3. **代价：多一层抽象**。真实供应商的某些能力可能无法映射到归一化模型
   （例如某家提供了我们模型里没有的字段）。处理方式是：
   把额外信息存进 `provider_snapshot` 原始响应，**不急于扩展主模型**——
   等到确实需要它时再扩，而不是为了「不浪费」而扩。
4. **Mock 数据需要足够真实**。用真实公告的脱敏样本构造，而不是随手编的字符串。
   Mock 太理想会让 P1 的评测数字虚高，选型时才发现落差。

## 风险

Mock 与真实供应商的差距可能在 P1 结束后才暴露（典型表现：`recall@10` 在 Mock 上
0.85，换真实数据后掉到 0.70）。

缓解：P1 期间用 **EDGAR 的真实数据**跑通同一条管线。EDGAR 免费、结构化程度高、
数据真实，能在没有 A 股公告供应商的情况下提供一个真实语料的检验基准。
`eval_retrieval` 的 100 条中要求至少 30 条基于 EDGAR 真实文档。

## 推翻条件

- 供应商选定且合同签署后，若只需要一家且明确长期不换，
  可以考虑简化抽象层（但**不建议**——契约测试的价值在换供应商之外，
  它同时保护我们免受上游格式变更的影响，见 `04-ingestion.md` §6）；
- 若所有候选供应商的六项能力都不达标，重新评估方案 C（自建解析）
  的可行性与合规边界；
- 若归一化模型被证明无法表达某家供应商的核心能力（例如提供了段落级的
  实体标注），应扩展模型并写新 ADR，而不是绕过抽象层。
