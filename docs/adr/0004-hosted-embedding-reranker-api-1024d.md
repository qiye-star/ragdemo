# ADR-0004 · 嵌入与重排走托管 API，向量维度固定 1024

- 状态：已接受
- 日期：2026-09-21
- 决策者：创始团队

## 背景

检索管线需要两个模型：嵌入模型（`bge-m3` 或 `Qwen3-Embedding`）用于离线批量向量化，
重排模型（`bge-reranker-v2-m3`）在每次查询的热路径上运行。

约束：起步期数据 + 模型预算 ≤ 5000 元/月（`00-overview.md` §3），
团队没有专职运维，数据须境内存储。

简报 §12 第 4 问：本地部署还是走 API，维度是否定 1024。

## 备选方案

**A. 全部走托管 API**
国内可备案平台提供 `bge-m3` 与 `bge-reranker-v2-m3` 的推理服务。

**B. 嵌入走 API、重排本地部署**
重排在热路径上，本地部署可消除网络延迟与限速；嵌入是离线批量，走 API 更划算。

**C. 全部本地部署**
需要 GPU 或至少一台常驻高内存机器。

## 决策

**选 A，维度固定 1024。**

方案 C 在起步期直接被预算否决：一张常驻 GPU 的月成本就接近全部预算。
方案 B 的理由（消除热路径延迟）是成立的，但它假设 API 的延迟不可接受——
这个假设**尚未被数据证明**。起步期先走 A，用 `06-retrieval.md` §9 的
`p95_latency < 3s` 指标检验；若重排 API 的延迟或限速成为瓶颈，
再按方案 B 把重排本地化。

这是一个「先测后优化」的决定，不是「永远用 API」的承诺。
适配器接口（`Embedder` / `Reranker` 协议）从第一天就存在，切本地不改业务代码。

### 为什么固定 1024

- `bge-m3` 原生输出 1024 维；
- `Qwen3-Embedding` 支持 MRL（Matryoshka 表示学习），可截断到 1024 维
  且质量损失有限；
- 两者因此**可互换而不需要改表结构**——更换嵌入模型只需回填向量
  （`05-document-pipeline.md` §7.3），不需要数据库迁移；
- 1024 维在 pgvector 的 HNSW 索引上下文内（上限 2000 维），索引可用。

固定维度的价值在于它把「换模型」从架构变更降级为数据回填。

## 后果

1. **首次全量入库受限速约束**。P1 有数十万块待嵌入，必须有批处理、
   内容哈希缓存、断点续传（`05-document-pipeline.md` §5.3）。
   这不是优化，是能否完成 P1 的前提。
2. **重排失败必须降级不中断**。API 超时或失败时回退到 RRF 顺序并标记
   `reranked=false`（`06-retrieval.md` §5）。降级发生率是需要监控的指标——
   持续降级就是切方案 B 的信号。
3. **写入前必须 L2 归一化**，因为 HNSW 索引用 `vector_cosine_ops`
   （`02-data-model.md` §5.4）。查询端也要归一化，两端不一致会静默返回错误的排序。
4. **数据出境风险需确认**。所选平台必须是境内节点，且服务条款不得包含
   「用户数据用于模型训练」。这是采购时的必检项，不是技术问题。
5. 更换嵌入模型需要全量重算向量，走 `05-document-pipeline.md` §7.3 的
   双列灰度流程，**不允许原地覆盖**。

## 推翻条件

- `p95_latency` 持续超过 3s，或重排降级率超过 5% → 重排本地化（方案 B）；
- 月度嵌入/重排 API 支出占预算比例超过 40%，而本地部署的摊销成本更低；
- 合规要求数据不得离开本机（私有化客户的硬性要求）→ 本地部署，
  此时 1024 维的固定选择让切换只需更换端点；
- 出现显著优于 `bge-m3` 且原生维度不是 1024 的模型，且 MRL 截断损失过大——
  此时需要评估是否值得做一次数据库迁移。
